= Pollerd reload, event tree locks, and listener metrics

== Poller configuration reload

Reloading Pollerd via `reloadDaemonConfig` (for example `opennms:reload-daemon Pollerd`) now refreshes poller packages in place:

* Reloads `poller-configuration.xml`
* Rebuilds package IP filter maps
* Calls `refreshServicePackages()` on existing pollables

It no longer runs a global `rescheduleAllServices()` walk that unschedules every service. That path could block the single Poller event thread for a long time under load.

For structural package or filter changes that require new pollables, rely on provision/category events or restart Pollerd.

== Event tree lock timeout

Administrative work on the pollable tree (delete, reconcile, category sync) waits up to `eventTreeLockTimeout` milliseconds for each node's fair lock. The default is `60000` (60 seconds) on the root `poller-configuration` element.

Poll workers still use a 500 ms lock wait and postpone when the lock is busy.

If the timeout is exceeded, the operation aborts with `LockUnavailable`. A Pollerd config reload emits `reloadDaemonConfigFailed` with the reason.

== Event listener JMX metrics

Eventd exposes per-listener metrics in JMX domain `org.opennms.netmgt.eventd`:

* `eventipc.listener.<ListenerName>.queued` — pending events for that listener
* `eventipc.listener.<ListenerName>.active` — active handler threads
* `eventipc.listener.<ListenerName>.onEvent` — timer for handler duration
* `eventipc.listener.<ListenerName>.rejected` — events discarded when the listener queue is full

For Pollerd, the listener name is `Poller:PollerEventProcessor` (sanitized in metric names as `Poller_PollerEventProcessor`).

A high `onEvent` duration with a low queue depth often means the handler is stuck inside one event (for example a long reconcile), not that the queue is backing up.
